# M6b — MySQL relocation and logical backup/restore drill
# Portable MySQL 8.0.46, 127.0.0.1:3307, run with the administrator credentials in
# .env.mysql-admin.local. No credential value appears in this file.
# The live schema was never dropped, renamed or reinitialised. The scratch schema created
# for the drill was dropped at the end (section 7).
# UTC timestamps are quoted where the command produced one.


## 1. Why this was done

B13 in tests/test-plan.md recorded two open items: the portable database lived in a
temporary directory, and no backup-restore drill had ever been run. A local Windows test
instance is not evidence that data survives, and a directory the operating system is free
to clean is not a place to keep records a report depends on.

Incident that proved the point. During M6b test runs the background QA server exited with
code 1073807364. The cause was not the site: the `bin`, `lib` and `share` folders of the
portable distribution had been removed from `%TEMP%` while its `data` folder survived, which
killed `mysqld` and every server that connects to it. Recovery used the original
`mysql-8.0.46-winx64.zip`, which had not been cleaned, and started `mysqld` against the
untouched data directory. `--initialize` was deliberately not run; against a populated
directory it would have destroyed the existing orders. All 125 orders were still there.


## 2. Relocation

The distribution was copied to a durable, deliberately managed location and restarted
against the same data directory.

    before: C:/Users/jackc/AppData/Local/Temp/saleshi-mysql/mysql-8.0.46-winx64
    after : D:/saleshi-mysql          (bin, lib, share, data, backups, source zip)

    $ mysql -e "SELECT VERSION(), @@datadir, @@basedir, @@port;"
    version   datadir                basedir            port
    8.0.46    D:\\saleshi-mysql\\data\\   D:\\saleshi-mysql\\   3307

Both `mysqld.exe` processes on the machine resolve to `D:\saleshi-mysql\bin\mysqld.exe`
(Win32_Process.ExecutablePath), so nothing is still running from the temporary copy.

The copy of the old tree was renamed rather than deleted, because a second plausible-looking
`data` directory is exactly the hazard that caused the incident above:

    C:/Users/jackc/AppData/Local/Temp/saleshi-mysql_STALE_moved-to-D-drive-2026-10-31

It is stale by design and Windows is free to clean it. Nothing reads from it.


## 3. Dump

    $ mysqldump --single-transaction --databases saleshi \
        > D:/saleshi-mysql/backups/saleshi-20261031T003401Z.sql

    saleshi-20261031T003401Z.sql   43,312 bytes
      sha256 dd588243f817bbb814dc0a2eb94d6a26eb474715b5c2367d23606756c5cacc8d
    drill-20261031T004047Z.sql     43,312 bytes (dump taken for the drill below)
      sha256 39df71ddef8d0d5afe390ddb38aa6109ea7b468d730cc2e50316d1497e55d0f5

The two dumps are byte-for-byte identical apart from mysqldump's own
"-- Dump completed on ..." comment line:

    $ diff <(grep -v 'Dump completed' saleshi-20261031T003401Z.sql) \
           <(grep -v 'Dump completed' drill-20261031T004047Z.sql)
    IDENTICAL apart from the completion timestamp comment

`--single-transaction` keeps InnoDB consistent without locking the tables, so the dump was
taken while the site was running.


## 4. Prepared for restore into a scratch schema

`mysqldump --databases` emits `DROP DATABASE IF EXISTS` and `CREATE DATABASE` for the real
schema name. Importing that file unedited would have deleted the live database, so those
statements were removed and the `USE` target rewritten before anything was executed. The
result was inspected, not trusted:

    $ grep -cE '^(CREATE DATABASE|DROP DATABASE)' drill-scratch.sql
    0
    $ grep -n '^USE' drill-scratch.sql
    23:USE `saleshi_restore_drill`;


## 5. Restore

    $ mysql -e "CREATE DATABASE saleshi_restore_drill CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
    $ mysql < D:/saleshi-mysql/backups/drill-scratch.sql

The import completed with no errors and no warnings.


## 6. Compared live against restored

Row counts. `information_schema.TABLES.TABLE_ROWS` was not used for this: it is an InnoDB
estimate and reported 0 for tables holding 125 rows.

    tbl            live    restored
    games          1       1
    offerings      1       1
    orders         125     125
    order_lines    125     125

Money. `total` is on `orders`; `unit_amount` and `line_total` are on `order_lines`.

    live.orders           125     845.50
    drill.orders          125     845.50

Content digests, so the comparison is over values and not only counts:

Constraints survived the text round trip:

    foreign keys on the restored schema   3   (order_lines -> orders, order_lines -> offerings,

All four digests match, all amounts match, and the restored schema carries the same
constraints and indexes.

## 8. What this proves, and what it does not

Proves: the relocated instance serves the site from `D:`, the dump restores into a fresh
schema with identical rows, totals, content digests, foreign keys and indexes, and a
mis-targeted `CREATE DATABASE`/`DROP DATABASE` in a dump file is a real hazard that has to
be checked before import.

Does not prove: this is a backup strategy. It is one logical dump on one workstation.
Scheduled dumps, off-machine storage, retention, point-in-time recovery, restore drills
against production-sized data, an upgrade path from the older M5 schema, and failover are
still open, and none of it is a hosted deployment. See docs/deployment-options.md.

Everything here was measured on a local portable instance with synthetic, simulated
orders. No real payment and no production data are involved.
